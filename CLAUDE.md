# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lanavix — an AI workforce SaaS for local service contractors (HVAC, plumbing, roofing, cleaning, etc.). Three core products: Missed-Call Text-Back (AI receptionist that texts back missed calls in ~60s), Reputation Autopilot (review requests + AI review-response writer), and Local Lead Generator (Google Places-sourced prospecting with AI-personalized outreach). Built on TanStack Start + Supabase + Stripe + Twilio + Anthropic, deployed to Vercel.

## Commands

```bash
npm run dev      # vite dev server
npm run build    # vite build — ALSO regenerates src/routeTree.gen.ts, run this after adding/removing routes
npm run lint     # eslint .
npm run format   # prettier --write .
npx tsc --noEmit # typecheck (no separate "test" script exists in this repo — there is no test suite)
```

There is no test framework configured (no `test` script in package.json, no test files in the repo). Correctness is checked via `npx tsc --noEmit` and manual verification.

`npx tsc --noEmit` has a standing baseline of **19 pre-existing errors**, unrelated to any single feature:
- `src/lib/onboarding.functions.ts` and `src/lib/leadblast.functions.ts` are legacy/broken — `leadblast.functions.ts` has zero importers anywhere (dead code, and its prompt asks Claude to invent fake businesses — exactly what the real Lead Generator was built to replace) and `onboarding.functions.ts` (used by `OnboardingWizard.tsx`) references profile columns that no longer exist.
- Four errors in `app.receptionist.tsx` / `app.reputation.tsx` are nullable-DB-column-vs-non-nullable-state-type mismatches.

Run `tsc` before and after any change to confirm you're still at 19 and haven't introduced something new — don't spend time "fixing" the baseline itself unless specifically asked.

## Architecture

### Routing

TanStack Start file-based routing under `src/routes/`. `src/routeTree.gen.ts` is auto-generated by `npm run build` (or the dev server) — **never hand-edit it**; regenerate it after adding/removing any route file.

- `src/routes/_authenticated/route.tsx` — the auth guard. Uses `supabase.auth.getSession()` (not `getUser()`) in `beforeLoad`, deliberately: `getSession()` reads the persisted session and silently refreshes the token, while `getUser()` makes a live network call that was previously bouncing users to `/auth` on transient network flakiness.
- `src/routes/_authenticated/app.*.tsx` — the authenticated dashboard (Overview, Receptionist, Campaigns, Calendar, Reputation, Network, Business Facts, Settings, Admin). `app.tsx` is the sidebar shell.
- `src/routes/api/**` — server-only route handlers (`createFileRoute(...).server.handlers.{GET,POST}`), the pattern used for essentially everything: Twilio webhooks, the AI generation endpoints, business-facts sync, admin batch jobs.
- Root marketing/public pages live directly under `src/routes/` (index, pricing, about, legal pages, `/audit`, `/chat`).

### Two server-side patterns coexist

Most business logic lives in plain `createFileRoute` server route handlers under `src/routes/api/`. A smaller, older set of functions (`src/lib/agents.server.ts`'s orchestrator, `onboarding.functions.ts`) uses TanStack's `createServerFn` + `createMiddleware` instead (see `requireAdmin` in `src/integrations/supabase/require-admin.ts`). Don't be surprised to see both — new work should follow the `createFileRoute` route-handler pattern, which is what every route in `src/routes/api/` other than the legacy orchestrator uses.

### Auth: two independent layers, don't confuse them

- **Client-side `useRequireAdmin()`** (`src/lib/admin.ts`) — a UI-only redirect based on a hardcoded `ADMIN_EMAILS` list. This is convenience, not security; it does not protect any data.
- **Server-side enforcement** — every real admin check happens server-side against `profiles.is_admin`: `requireAdmin` middleware (for `createServerFn` handlers) or `authenticateAdmin()` in `src/lib/admin-auth.server.ts` (for plain `createFileRoute` handlers, which don't go through TanStack middleware). Any new admin-only route needs the server-side check — the client redirect alone is not a security boundary.

Regular (non-admin) API routes authenticate by reading a bearer token off the `Authorization` header and calling `supabaseAdmin.auth.getUser(token)` — see any file under `src/routes/api/business-facts/` or `src/routes/api/review-response.ts` for the canonical shape.

### Supabase: two clients, on purpose

- `src/integrations/supabase/client.ts` — anon/publishable key, respects RLS. Used everywhere in client components.
- `src/integrations/supabase/client.server.ts` — service-role key, **bypasses RLS**. Server-only; every file that imports it is named `*.server.ts` by convention (`activityLog.server.ts`, `businessFacts.server.ts`, `twilio.server.ts`, `stripe.server.ts`, etc.) specifically so it's obvious at a glance which files must never be imported into client-bundled code.

### Database migrations: the `supabase/migrations/*.sql` folder has drifted from the live database

Confirmed directly against the live project (`fnmmojfvxbdupzigcnyw`, via the Supabase MCP server): `public.update_updated_at_column()` is referenced by several older migration files as a shared "touch updated_at" trigger function, but **it does not actually exist in the live database**. Don't assume anything in this folder is an accurate 1:1 history of the live schema — when in doubt, check the live project directly (`mcp__Supabase__execute_sql` / `list_tables`) rather than trusting the migration files alone. New tables that need `updated_at` maintenance set it explicitly in application code rather than depending on a trigger.

`check_rate_limit` / `check_anon_rate_limit` (used throughout `src/routes/api/**` for per-user/per-IP rate limiting) are live Postgres functions with **no corresponding migration file in this repo at all** — another example of the same drift. They exist and work; just don't go looking for their SQL definition locally.

When making schema changes: apply via the Supabase MCP server (`apply_migration` against project id `fnmmojfvxbdupzigcnyw`), then regenerate `src/integrations/supabase/types.ts` with `generate_typescript_types` and check the security/performance advisors (`get_advisors`) before moving on — a bare `auth.uid()` in an RLS policy gets flagged immediately for being re-evaluated per-row instead of once per query; use `(select auth.uid())` instead.

### RLS pattern

Every per-business table uses the same shape: `user_id uuid not null references auth.users(id) on delete cascade`, RLS enabled, and a single `for all using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id)` policy. Admin-readable tables (`verification_documents`) add separate admin policies checking `profiles.is_admin` on top. Follow this shape for any new per-business table rather than inventing a different one.

### Design system split: marketing pages vs. authenticated dashboard

Marketing/public pages (`index.tsx`, `pricing.tsx`, `about.tsx`, legal pages) use real Tailwind utility classes and shadcn/ui components (`@/components/ui/*`) — this is the "correct" pattern for this codebase.

Most authenticated dashboard pages (`app.index.tsx`, `app.calendar.tsx`, `app.network.tsx`, etc.) instead use inline `style={{ ... }}` objects referencing CSS custom properties defined in `src/styles.css` (`var(--foreground)`, `var(--card)`, `var(--primary)`, `var(--accent)`, `var(--muted-foreground)`, `var(--destructive)`, `var(--accent-2)`, etc.) rather than Tailwind classes. Only `app.settings.tsx` and the `app.tsx` shell actually use the Tailwind+shadcn pattern in the authenticated app. When adding a new dashboard page, match the inline-style-with-CSS-vars pattern the other dashboard pages already use — it's the de facto standard there even though it isn't the "better" pattern used on the marketing side. The available tokens are intentionally a small palette (green primary/accent-2, red destructive, neutral muted/foreground) — don't invent new hex colors for a status/badge system; map onto the existing tokens even if that means two different states share a color.

### The `business_facts` system — per-business "AI memory" (built 2026-07-26)

Foundation for grounding AI-generated customer replies in real, contractor-confirmed facts instead of generic non-answers.

- **Table**: `business_facts` (`user_id`, `fact_type`: service/pricing/hours/service_area/general, `fact_text`, `source`: setup_form/google_synced/website_synced/auto_learned, `status`: active/pending_review/rejected). Indexed on `(user_id)` and `(user_id, fact_type)` since every read path filters on both.
- **Conflict rule (deliberately simple for v1, not AI-judged)**: syncing a fact type with no existing active fact of that type → goes `active` immediately. An active fact of that type already exists with different text → new one goes to `pending_review` for a human to reconcile. An exact duplicate of an existing active fact → skipped (so repeat syncs don't pile up).
- **Sync is manual-only, not automatic**: `POST /api/business-facts/sync-google` and `POST /api/business-facts/sync-website` are both "Sync now" buttons the contractor clicks — there is no Vercel Cron or scheduler running these periodically. This was a deliberate choice, not an oversight: two admin batch endpoints already in this codebase (`api/admin/update-scores.ts`, `api/admin/update-pricing-index.ts`) were built the same "periodic" way in an earlier session and **never actually got wired to a scheduler** — if automatic sync is added later, wire real Vercel Cron rather than repeating that pattern.
- **`profiles.website`** (pre-existing, previously dead/unused) is reused for the confirmed website URL rather than adding a duplicate column. `profiles.google_place_id` is new. A contractor can't reasonably supply a raw Google Place ID, so `POST /api/business-facts/search-google-places` lets them find their real listing by name+city and confirm it from a short list.
- **Real-data principle** (this is the `lanavix-growth-engine` skill's Rule 1, and it governs this whole feature): the website-sync AI extraction prompt only pulls facts literally printed on the page — untrusted page content is delimited and explicitly labeled "data, not instructions" in the prompt (same defense pattern as `review-response.ts`), and the model is told never to infer or invent. This same principle is why the Lead Generator's AI calls only ever synthesize copy from real Google Places data and never "find" or invent businesses/phone numbers/emails.
- **SSRF guard**: `isSafeExternalUrl()` in `src/lib/businessFacts.server.ts` blocks the website-sync fetch from reaching localhost or any private/link-local IP range (including the cloud metadata address `169.254.169.254`) before it ever fetches a contractor-supplied URL server-side.
- **Wired into Missed-Call Text-Back**: `sms-reply.ts` fetches the business's active facts in one query (scoped by the indexed `user_id` column, capped at 40 rows to bound prompt size) and includes them in the AI receptionist's system prompt — real facts now override the old blanket "never make up a price" instruction for anything the facts actually cover.

### Environment variables

`src/lib/env.server.ts` is the single source of truth for every env var this app uses, with per-category required/optional flags and validators — read it rather than guessing what's needed. Notably: there is no `DATABASE_URL` (Postgres access is only ever through the Supabase SDK) and no separate auth secret (Supabase Auth manages its own session signing). Billing (Stripe) env vars are all optional right now because the real Solo/Crew/Agency Stripe products haven't been created yet (see `scripts/setup-stripe-products.mjs`) — billing is functionally on hold independent of whether the keys are set.

### Deploy target is Vercel, not Cloudflare

`nitro.config.ts` and local builds produce Cloudflare/wrangler artifacts (`.output/server/wrangler.json`, the "Wrangler config main is overridden" build warning) — this is just the Lovable Tanstack config wrapper's hardcoded local fallback preset when no `VERCEL` env var is present to auto-detect. The real, working deploy target is Vercel (see `vercel.json`, `DEPLOY.md`). Ignore the wrangler output; it's not what production runs.

### Git workflow

Development happens on a feature branch (check current branch before starting work — don't assume `main`); merge to `main` only when explicitly asked, and push triggers an automatic Vercel production deployment. Commit each distinct fix/feature individually with a descriptive message rather than batching unrelated changes into one commit — this repo's history is a genuine record of incremental, verified changes (each one typically preceded by an `npx tsc --noEmit` check against the known baseline), not a single squashed dump.
